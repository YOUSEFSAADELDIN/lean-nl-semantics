# Blind evaluation: methodology, current coverage, and limitations

This records what "blind evaluation" actually tests in this project, the
exact current coverage and result (CI-confirmed, not estimated), what it
deliberately excludes and why, and how the resulting number does and does
not compare to prior published FraCaS accuracy figures (e.g. FraCoq's
83%/81%). It exists as its own document rather than another paragraph in
`README.md` because the real content here is the reasoning and the exact
breakdown, not just a headline number — the number alone, without this,
invites exactly the "comparable to FraCoq?" question this document
answers directly.

## The concern this addresses

Every one of the 342 formalized FraCaS problems in this corpus is proved
by a human who already knew, from FraCaS's own gold answer, which
direction to prove: `theorem fracas_002 : Every P Q → Some P R → Some P Q
:= every_some ...` bakes in a decision no automated procedure made. The
338/342 "self-consistency" figure this project otherwise reports is a
check that each hand-written proof's *shape* matches its recorded gold
answer — a manual audit, not a blind prediction. It says the
formalizations are internally consistent, not that an automated system
correctly inferred each one's answer from the premises and hypothesis
alone.

Blind evaluation is the attempt to close that specific gap: take a
problem's translated premises/hypothesis (the `Prop` the human wrote,
unavoidably a translation choice, same as any NLI system's parsing step)
and let fixed, general-purpose tactics — not the human's proof — decide
which direction holds, then compare that automated decision against gold.

## Methodology

### Bare entailment-shaped theorems (`BlindEval.lean`)

For every `fracas_NNN` theorem (no suffix — see "Scope" below for what a
suffix excludes) whose conclusion, after introducing its implication
chain, is headed by one of `Every`/`Some`/`No`/`Most`/`AtLeast`/`AtMost`/
`Both`/`Neither`/`Exactly`:

1. Take the theorem's own type only, never its proof term.
2. Attempt to close that type directly (**pos**: premises → hypothesis?)
   and, separately, the type with its hypothesis negated (**neg**:
   premises → ¬hypothesis?), via the identical fixed tactic chain both
   times: this corpus's certified monotonicity fragment (`mono_nl`,
   `exist_nl`, `mono_nl_compose` — see `Tactic.lean`/`Existential.lean`/
   `Compose.lean`), then two small targeted searches for `Most`-headed
   goals (`most_nl`, `every_most_nl`), then one `aesop` call armed with
   every general (not problem-specific) `GQ.lean`/`Plurals.lean` lemma,
   then `grind` as a last resort.
3. (pos succeeds, neg fails) → **yes**; (neg succeeds, pos fails) →
   **no**; (neither succeeds) → **unknown**; (both succeed) → a flagged
   **contradiction**, never silently folded into yes or no.
4. Compare against FraCaS's own gold `Answer`, collapsing `.unknown` and
   `.undef` both onto automated `"unknown"` (a binary yes/no/unknown
   procedure has no way to tell "genuinely undecided" apart from "the
   source's answer wasn't a literal yes/no/don't-know").

### Countermodel-pair `.unknown`/`.undef` problems (`BlindEvalUnknownScan.lean`)

Every genuine `.unknown`/`.undef` problem in this corpus is represented
not as a single theorem but as a `_dir1`/`_dir2` pair: two concrete
models (over `Bool`, `Fin n`) jointly witnessing that neither direction
is a validity. That pair has no single entailment-shaped `Prop` the
procedure above could even pose a yes/no question about, so
`BlindEval.lean` skips every one of them by construction.

The fix is not to force them into that shape but to recognize what a
genuine independence claim actually is: by construction, not a valid
universal statement in either direction, so there is no theorem to write
down and prove — and no proof burden to invent one. Each of the 46
`.unknown`/`.undef` problems in Sections 1–2 instead gets a bare,
deliberately **unprovable** `Prop`-valued `def`
(`BlindEvalUnknown.lean`, generated by `scripts/gen_blind_eval_unknown.py`):
the generic, schematic form of exactly what that problem's own, already-
proved `dir1`/`dir2` pair demonstrates concretely, with the quantifier
structure put inside the `Prop` itself (`∀ {A}[Fintype A] (P Q)[...],
AtMost 2 P Q → Some P Q`, for instance) so the existing `attemptClose`/
`negateConclusion`/`introAll` machinery can consume it exactly like a
bare theorem's type, with no new extraction logic. Each generic claim is
a mechanical generalization of its own dir1/dir2 pair — every concrete
predicate or individual promoted to a free schematic variable, the same
variable reused wherever the identical concrete term recurs across both
models — not a fresh translation from the English, though cross-checked
against the English directly for the handful of multi-premise chains
where position-sharing alone was ambiguous (ids 28, 34–37, 42, 43, 65).

The scan then runs the exact same `attemptClose`/`negateConclusion`
pipeline (factored into `BlindEvalCore.lean` so both scans share it)
against each claim, in both directions, and the correct automated
outcome is **failure on both** — that failure, not a yes/no verdict, is
what a genuine independence claim should produce, and is compared
against the gold `.unknown`/`.undef` answer the same way
`BlindEval.lean`'s own `answerMatches` already does.

## Current result (CI-confirmed)

FraCaS Sections 1–2 together cover 113 problems (80 in Section 1, 33 in
Section 2). Of those:

| | problems | automated verdicts matching gold |
|---|---|---|
| Bare yes/no, Section 1 | 37 | 37/37 |
| Bare yes/no, Section 2 | 10 | 10/10 |
| `.unknown`/`.undef` countermodel pairs, Sections 1–2 | 46 | 46/46 |
| **Total blind-evaluated** | **93** | **93/93 (100%)** |

All 46 `.unknown`/`.undef` problems in Sections 1–2 are covered — this is
every problem with that gold answer in these two sections, with none
left over. 0 contradictions and 0 mismatches across all three scans.
(Exact CI output: `blind_eval_section1`, `blind_eval_section2`,
`blind_eval_unknown` commands in `BlindEval.lean`/
`BlindEvalUnknownScan.lean`, run on every push.)

## What's still excluded, and why

**20 bare theorems in Sections 1–2 are not entailment-shaped** by this
procedure's own shape check (conclusion not headed by one of the
quantifier heads `blindEvalHeads` lists) — Section 1: problems 6, 14, 38,
46, 70; Section 2: problems 81, 82, 84, 85, 86, 89, 99, 101, 103, 105,
106, 109, 111, 112, 113. These use proof patterns outside this
procedure's current shape vocabulary (for instance the "two unconnected
concrete facts" pattern `Section4/Ellipsis.lean` documents, or
plural-specific constructions this scan's head list doesn't recognize).
Widening `blindEvalHeads` and the tactic chain to cover them is possible
future work, not attempted here.

**One further suffixed name** (`fracas_002_from_gf`, a `GFCrossCheck.lean`
demo re-derivation, not a distinct FraCaS problem) is correctly skipped
as non-bare and isn't a gap.

**Sections 3–9 (229 problems: anaphora, ellipsis, adjectives,
comparatives, temporal reference, verbs, attitude reports) are entirely
untouched.** Doing this for them is the genuinely substantial remaining
step: each section would need its own automated-tactic fragment
comparable to what `Monotonicity/` built for Section 1's GQ layer and
`Plurals.lean` extended to Section 2 — not a mechanical extension of the
existing fragment, which is grounded specifically in generalized-
quantifier monotonicity and has nothing to say about, e.g., temporal
ordering or attitude-report opacity.

## Comparison to FraCoq (83%/81%)

The 93/93 figure above is a genuine blind-prediction accuracy score in
the narrow sense that matters: the automated decision used only the
translated `Prop`, never the human's proof direction. But it is still
**not directly comparable** to FraCoq's reported 83%/81%, for two
reasons that both push in the same direction (this project's number
looks better than it should, by comparison):

1. **Coverage**: FraCoq's figures are over its full FraCaS treebank,
   essentially the whole suite (both sections' worth of two-way and
   three-way tasks). This project's 93/93 covers 93 of 113 problems in
   only Sections 1–2 — 27% of the full 342-problem suite, not all of it.
   A number this narrow in scope set against one covering the whole
   corpus is not an apples-to-apples comparison, regardless of either
   one's accuracy.
2. **Translation**: FraCoq's pipeline includes automated parsing from
   English into its logical form — its reported accuracy reflects
   mistakes in that step too. This project's premises/hypothesis `Prop`s
   are still hand-translated (the GF integration in `gf/` independently
   checks a translation step's own output against FraCaS's recorded
   English for a subset of Sections 1–2, but that is a translation
   *consistency* check, not inference). This project's blind evaluation
   therefore isolates and scores only the inference step, which is an
   easier, narrower problem than FraCoq's end-to-end score reflects.

A number actually comparable to FraCoq's would need both gaps closed:
blind evaluation extended through all nine sections (the real remaining
work flagged above), and an automated translation step's own output fed
into it rather than the hand-translated `Prop`s used here (the existing
`gf/translate.py` cross-check is the closest piece of infrastructure
toward that second gap, though it currently covers only a subset of
Sections 1–2 and was built to check translation fidelity, not to drive
blind evaluation end-to-end).

## Other limitations worth stating plainly

- The tactic chain (`mono_nl`/`exist_nl`/`mono_nl_compose`/`most_nl`/
  `every_most_nl`/`aesop`/`grind`) was built and iterated against this
  exact corpus. A 100% match rate on problems the chain was tuned
  against is a weaker claim than the same rate on a held-out set the
  chain never influenced — there is no such held-out set here, because
  there is only one FraCaS Sections 1–2 to evaluate against. This is a
  structural limitation of blind-evaluating a fixed, closed benchmark
  with a hand-built reasoner rather than a learned one; it does not mean
  the 93/93 result is invalid, only that it should not be read as
  evidence the chain generalizes to sentences outside this corpus's
  vocabulary and structure.
- `aesop`'s lemma list in `attemptClose` is general (not problem-
  specific) `GQ.lean`/`Plurals.lean` content, but it is still a list
  curated by a human who had already seen the whole corpus — the same
  "self-serving?" concern the axiom audit (`MTT/AssumptionAudit.lean`)
  raises for axioms applies here in a milder form. The genuinely
  independent part of this evaluation is which *direction* closes, not
  whether some member of a hand-picked general lemma set exists at all.
- A `.yes`/`.no` match only confirms the tactic chain picked the
  direction FraCaS also picked; it does not independently confirm that
  direction is linguistically correct (the hand-proof already is that
  confirmation, via the separate 338/342 manual consistency audit in
  `README.md`).
